AI 原理图解 2601 / 07
先定标准

先写清什么叫完成

评测前，先把任务写成能检查的样子。“整理客户反馈”太宽；“归类十条反馈，更新表格，不改原文”就能验收。

一项任务至少要交代输入是什么、交付物放哪里、完成后环境应该变成什么样。任务也要写明不能触碰的边界，比如不能把草稿发给客户。

验收可以拆成三个视角：

产物：分类有没有依据，摘要能否读懂
状态：表格是否真的更新，行数是否正确
边界：有没有改动原文、越权发送

标准越具体，失败时越容易知道要修哪一环。

AI 原理图解 2602 / 07
准备样例

用真实任务来试

评测样例是一组带有输入和成功条件的小任务。只拿最顺手的一题试，测不出日常会遇到的麻烦。

以整理反馈为例，正常样例可以给十条清楚的用户意见，检查分类和写表。再加入含糊的反馈、重复记录、缺少日期的记录，看看 Agent 会不会自行编造。

还要放进“应该停手”的样例：任务只要求生成草稿，Agent 就不能顺手发送。只读查询也不应修改表格。

每个样例都保存输入、初始环境、允许的操作和验收条件。下次改提示词或工具后，才有同一把尺子。

样例先从真实失败里收集，再补普通情形和边界情形。

AI 原理图解 2603 / 07
查结果

看产物，也看状态

Agent 的回复是交代经过，真正的结果还在文件、数据库或外部系统里。

比如 Agent 说“已更新反馈表”，要打开表格核对：是不是目标文件、有没有新增十行、旧记录有没有被覆盖、分类列是否填对。

产物质量可以用人工审阅或评分规则检查；行数、文件路径、字段值则更适合用可重复的程序检查。两种检查各管一块。

验收时给 Agent 一个独立的初始环境。前一次测试留下的文件或缓存，可能让这次结果看起来更好，也可能制造假失败。

若任务涉及发送、付款等外部动作，先在可控环境里验证，不拿真实用户当测试数据。

AI 原理图解 2604 / 07
查过程

过程记录能找到错处

一次执行通常会留下模型回复、工具调用、参数和工具返回。这些记录能解释结果为什么失败。

反馈表少了两行，可能是 Agent 漏读了输入，也可能是写表工具收到的行数就不对。只盯最后一段回答，分不清问题在哪。

读执行记录时，可以沿着任务走一遍：目标是否理解对，工具是否选对，参数是否指向正确文件，工具报错后有没有处理，最后有没有核查结果。

过程记录主要用来定位问题。只要结果与边界都满足，没必要把每一步固定成唯一的标准答案。

发现一次合理做法被评分规则判错，也要回头检查规则是否写得太死。

AI 原理图解 2605 / 07
多次运行

成功一次还不够

同一任务多跑几次，Agent 的执行路径和结果可能不同。一次跑通，只能说明“这一次成功”。

把同一组任务重复运行，记录每次是否达到验收条件。比如一项任务跑五次，四次更新正确、一次漏掉记录，就不能把它当成稳定完成。

统计时可以看单次成功率，也可以看“连续几次都成功”。面向真实用户的功能，后一项更接近使用时的感受。

重复测试前重置环境；否则上一次留下的状态会干扰结果。测到波动后，要读失败那次的执行记录。

运行成本和耗时也值得记录，但先确认任务做对，再比较谁跑得快。

AI 原理图解 2606 / 07
放在一起看

留一张最小验收表

准备几个真实样例，每次改 Agent 后照同一张表重测。失败样例要留下来，防止下次改好一处又坏一处。

任务与起点：输入、初始文件或数据状态
验收条件：产物、最终状态、禁止动作
执行证据：工具调用和关键返回
重复结果：每次通过与否、失败原因

可以先从最常见、最容易出错的任务各挑一两个。评测规模可以慢慢长，标准要先写清。

本章回顾：记忆、工具调用、工作流、续跑、人工确认，最后都要回到一件事：任务做完之后能不能验收。
