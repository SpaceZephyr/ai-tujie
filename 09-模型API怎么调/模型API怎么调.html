AI 原理图解 0901 / 07
必填的三样

三件套：调用的全部门槛

API 是程序之间约好的调用方式。调一次大模型，必填的东西少得出奇，就三样：往哪发、用哪个、算谁的钱。

base_url：模型服务的地址。用官方就填官方的，用云平台就填云平台的
model：模型名，指定这次让哪个模型干活。同一个地址下常有几十个可选
api_key：一串密钥，既是身份也是账单。谁拿着它，谁就能用这份额度

剩下的就是这次要发的内容，和几个调手感的参数。接入本身没什么复杂的，复杂的是接入之后：怎么控成本、怎么处理失败、怎么保证质量。

密钥有一条底线：绝对不能放进网页或 App 里。这些东西用户都能拆开看，密钥放进去就等于公开了，别人拿去随便跑，账单算在自己头上。

AI 原理图解 0902 / 07
发什么

消息：发给模型的对话

请求里的内容放在 messages（消息）里，是一串按顺序排好的消息。每条消息都标着是谁说的，常见的有三种身份：

system：系统提示，放在最前面，写产品的角色、语气、能做和不能做的事
user：用户说的话
assistant：模型之前的回答

模型自己不记得上一轮聊过什么。想让它接着聊，就得把之前的 user 和 assistant 消息一起再发一遍。聊得越久，每次发的内容越长，花的钱也越多。

system 每一轮都要带上，而且内容基本不变，所以最适合做缓存：把固定的内容放前面，会变的放后面，重复的部分就能按折扣价算。

AI 原理图解 0903 / 07
调手感

参数：几个调体验的旋钮

参数不多，但每个都对应一种用户能感觉到的问题。很多“模型不行”的抱怨，毛病其实出在参数上。

temperature：随机性。要输出稳定就调低，默认值往往偏高
top_p：另一种控制随机性的方式，一般和温度只调一个
max_tokens：输出长度上限，到了就硬停，回答会断在半句话
stream：流式输出，一个字一个字往外冒，等待感轻很多
response_format：强制返回 JSON 这类固定格式

厂商的默认值是按通用聊天调的。做客服就把温度调低；做数据抽取，温度调到最低，再打开 response_format；只要用户在盯着屏幕等，就把 stream 打开。

max_tokens 也管钱，输出比输入贵好几倍。最好按功能分别设，再在提示词里写上想要多长，比如“用三句话回答”，让它自己收着写，比硬截断体面。

AI 原理图解 0904 / 07
换厂商

通用格式：换厂商很方便

大部分模型平台，都兼容 OpenAI 那套接口格式。它出现得早、配套工具最多，后来的厂商要是另搞一套，客户迁过来就得重写代码，谁都不想设这个门槛。

好处很直接：换厂商，常常只要改 base_url 和 model 两处。所以工程师说“换个模型很快”，多数时候不是夸口。

不过有几件事要提前知道：

提示词要重调：接口通了，效果不一定一样
高级功能不一定通用：工具调用、缓存这些，各家细节不同
小心 -latest 这类名字：厂商一更新，调用就自动换成新版本

最后一条最难查：哪天效果和账单突然变了，大家都说没动过代码。线上环境最好固定到具体版本号，升级时当成一次正常发版来测。

AI 原理图解 0905 / 07
看返回

返回值：不只是一段回答

模型回来的，除了回答内容，还有两样常被忽略的东西：这次用了多少 Token，以及它为什么停下来。

usage 里记着输入和输出各用了多少 Token，钱就是按这个算的。把它按功能记下来，才知道哪个功能最费钱，也能早点发现有人在刷接口。

finish_reason 说明这次回答是怎么结束的，常见的几种：

stop：正常说完了
length：碰到 max_tokens 上限，被截断了
tool_calls：模型想调用一个工具，等着执行结果
content_filter：内容被安全过滤拦下了

看到 length，就别把这半截内容直接给用户看，可以放宽上限重试，或者提示内容太长。回答断在半句话，多半就是这个原因。

AI 原理图解 0906 / 07
调通之后

分档降级：不押一个模型

全站只用最强的那个模型最省事，但也最贵、最脆：大部分请求用不上那个档次，它一挂，所有功能跟着挂。

比较稳的做法，是按任务分几档：

轻档：分类、打标签、抽字段，小模型就够，又快又便宜
中档：问答、摘要、写内容，用主力模型
重档：多步推理、复杂代码，用推理模型，控制好占比

再给每一档配一个备用模型。备用要定期真跑一遍，切过去时统一输出格式，每次降级都记下来。这些事都在封面里那层自己的后端完成，从第一天就把模型调用封装起来，后面才改得动。

换模型、调档位、切备用之后，怎么知道效果没变差？留一组 20 到 50 条真实请求当测试题，每次改动都跑一遍，和上次的结果并排比。
