先算尺寸

台面有多大，一起算

上下文窗口是模型一次请求能看到的全部内容的上限。按 Token 算，不是按字数。中文通常一个 Token 对应一到两个字，代码则往往更少。

厂商标称的 128K、200K、100 万，指的是 Token 数，不是字数。一篇 10 万字的中文文档，大约需要 5–8 万 Token；同样长度的代码，可能要十几万 Token。要准数只能实测。

最容易忘的一点：输出也占窗口。标称 128K，把输入塞到 127K，模型就几乎没空间写回答了。做预算时，必须先给输出留出额度，剩下的才是输入能用的。

一个可以直接用的分配思路：

先扣输出额度：按允许的最长回答估算，再留余量
再扣系统提示：固定值，算一次就行
剩下的：在“历史对话”和“检索资料”之间分
AI 原理图解 1002 / 07
台面里有什么

很多东西不是你自己塞的

很多人以为窗口里只有对话。实际上，一次请求发过去的内容，大部分不是用户自己写的。

系统提示：产品的设定和规则，每一轮都要重发。历史对话：之前所有的来回，包括工具调用的结果，越聊越长。检索资料：RAG 塞进来的文档片段，往往是最大的一块。

真正由用户控制的部分，通常只有本轮输入和上传的文件。其余都是平台或产品在背后自动拼装的。

想知道一次请求到底发了多少 Token？看返回里的 usage 字段。很多产品不展示这个数，但 API 里一定有。
AI 原理图解 1003 / 07
超出上限

装满了怎么办

窗口有硬上限，超了必须处理。两种结局，第二种更隐蔽、更危险。

直接报错
请求发不出去，平台返回错误码。至少知道出问题了，可以处理。
静默丢弃
很多框架自动裁掉最早的内容，让请求能发出去。没有提示，没有日志。

问题在于，最早的内容往往正是最重要的——开头定好的规矩、任务的原始描述、双方确认过的约束。丢掉之后，模型表现就开始漂移。只会觉得“今天有点笨”，查不出原因。

所以有一条实践纪律：搞清楚用的框架在溢出时到底做了什么。是报错，还是裁剪？裁的是哪一头？有没有日志？这个答案，决定了以后能不能查得清问题。

AI 原理图解 1004 / 07
中段丢失

中间那段最容易被忽略

上下文窗口不是均匀的画布。同样一句话，放在开头或结尾，和埋在中间，被用上的概率差别很大。

这个现象在业内叫 lost in the middle，不是某一家模型的 bug。上下文越长，中段越容易被忽略。长提示词中间写的限制，RAG 召回十几段资料时中间的那些段，都可能被当没看见。

应对方法：重要的东西放两头；关键约束在开头写一遍、结尾再强调一遍；宁可召回 5 段精准的，不要 20 段掺水的。

AI 原理图解 1005 / 07
不是越大越好

窗口大不等于都能用上

现在动辄百万级窗口，很多人以为“把所有东西都塞进去”就解决问题了。不是。三个原因。

塞得下不等于看得清。内容一长，中间那段会被明显忽略——上一页专门讲这件事。塞一百页进去，模型可能只真正用上了开头和结尾。

贵。整个上下文每一轮都要重新发送、重新计费。一段 50K Token 的资料，聊十轮就是 50 万 Token 的输入量。长窗口的账单增长很吓人，尤其在 Agent 多轮循环的场景里。

慢。输入越长，首字延迟越明显，用户能感觉到。

正确的思路不是“窗口够大就全塞”，而是只塞真正需要的那几段。检索的意义不只是找到资料，更是只把相关的那几段放进来。
AI 原理图解 1006 / 07
连起来看

窗口管理的三件事

把窗口当成一份要分配的预算，而不是一个想填多满就多满的桶。该给的、不该给的，比给得多重要。

第一件，做预算：先扣输出额度，再扣系统提示，剩下的在历史对话和检索资料之间分。给检索资料设硬上限，历史对话超过阈值就压缩。

第二件，控制位置：重要的放两头，关键约束重复一次。长任务拆成几轮，每轮上下文都短，中段丢失就不成问题。

第三件，控制数量：宁可少而精，不要多而杂。召回 5 段准确的，通常胜过 20 段良莠不齐的。
