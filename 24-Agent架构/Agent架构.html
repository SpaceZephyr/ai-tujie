先看核心

模型拿到了什么

模型是 Agent 的决策核心。开发者选模型、写指令、提供工具说明；运行时再放入用户任务和当前上下文。模型看到什么，会影响下一步怎么选。

指令通常写角色、目标和边界，比如“先查询订单，再判断退款条件”。当轮上下文则带着用户原话、前面说过的内容、工具返回的订单信息。

模型可能直接回答，也可能输出一次工具请求。它给出调用意图和参数；程序检查后才会真正执行。这个分工能把模型的判断和外部动作分开。

如果工具列表里没有“查订单”，模型就无法通过这条通道取得实时订单状态。即使能把话说得很像，也不能拿生成的文字当查询结果。

同一个模型，换一套指令、上下文和可用工具，能承担的任务也会变。Agent 的能力不只来自模型本身。

执行中心

运行器管整场执行

运行器可以理解为外面的程序。它负责调用模型、识别模型返回了什么、执行工具或交接任务，再把结果送进下一轮。

模型发出“查订单”的请求后，运行器找到对应工具。工具返回订单详情，运行器把结果加进上下文，再请模型决定下一步。模型给出最终答复，或触发停止条件，这次任务才结束。

一些 SDK 把这些工作封装进 Runner；自己用模型 API 搭建时，也要在程序里处理回合、工具、异常和退出条件。运行器是架构里的执行者和调度者。

运行器还能在不同 Agent 之间交接任务。比如一个 Agent 负责接待，遇到退款请求时转给专门处理订单的 Agent；程序需要把必要的上下文一起交过去。

此前的“Agent 循环”讲一轮怎么转，这里看的是谁让每一轮接起来，以及任务跑偏、工具失败时谁来处理。

外部能力

工具接上真实世界

模型的回答只是一段输出。要查订单、搜网页或修改文件，得把这些动作做成工具，交给运行器执行。

工具要有清楚的用途、参数和返回格式。以“查订单”为例：模型填入订单号，程序校验参数和权限，调用订单系统，再把查到的状态返回。模型随后才能依据真实结果继续处理。

工具也有风险等级。查询类可以先开放；退款、发消息、删除文件这类会改变外部状态的动作，需要更严格的权限或人工批准。

查不到订单时，工具最好返回明确的失败原因。模型拿到“订单号不存在”，才能决定询问用户还是停止；模糊的空结果容易让后续判断走偏。

此前的“工具调用”细讲一次请求如何往返。在架构图里，只要记住它的位置：工具是通往外部世界的接口，执行权在程序一侧。

任务进度

状态决定能否续上

Agent 跑多轮时，下一次模型调用需要知道前面发生了什么。这些对话、工具结果和任务进度，合起来就是要管理的状态。

最简单的做法，是每轮把历史消息重新带给模型。SDK 也可以用 session 保存会话历史。跨任务要长期使用的事实，则要另外设计存储、检索和更新方式。

例如退款 Agent 查完订单后中断，恢复时至少要知道查的是哪一单、结果是什么、退款动作有没有执行。否则可能重复调用工具，甚至重复操作。

所以除了对话历史，还可以保存一份结构化任务状态：订单号、当前步骤、已完成动作和待确认动作。下一次运行先核对这份记录，再决定能否接着做。

会话记录能保留上下文，长任务的可靠续跑还需要记录具体执行状态。“记住说过什么”和“知道做到了哪”是两件事。

架构外圈

安全与记录要跟上

Agent 能调用外部服务后，不能只看最终回答。输入和输出要校验，敏感动作要管权限，运行过程要能追溯。

护栏可以检查用户输入、工具调用条件和最终结果。退款这类动作还应在执行前暂停，交给人确认。运行器也需要设置最大回合数或其他停止条件，防止任务一直转下去。

轨迹会记录模型调用、工具请求、工具结果和交接等事件。出了错，才能定位问题发生在模型判断、工具执行，还是状态恢复。

例如发现用户收到两次退款通知，只看最终答复查不出原因；把工具调用和恢复记录串起来，才能确认是模型重复请求，还是程序重复执行。

这几项包在整个执行过程外面。 它们不替模型做决定，但决定了系统是否可控、可查、能停。

放在一起看

先搭一条短链路

把退款例子放回图里：用户提需求，模型根据指令与订单信息决定下一步；运行器组织回合；工具负责查单和执行；状态保存已经做过的事。

若从零搭建，可以先让 Agent 只查询订单并给出处理建议。确认读工具、上下文和轨迹都工作正常，再接入退款动作，同时补上权限和人工批准。

每加一项能力，都要想清它归哪层、由谁执行、出错后怎么查。 架构图的用处，是让职责边界看得见。
